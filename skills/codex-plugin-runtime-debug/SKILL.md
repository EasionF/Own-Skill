# Codex 插件运行时排障

当出现以下情况时使用本 skill：

- 已经有 `SKILL.md`，但实际工具不可调用
- 本地 plugin 文件已经创建，但 Codex 运行时没有加载
- hook 配了 `hooks.json`，但没有触发
- 重启后仍然没有生效
- 不确定问题出在 skill、plugin、安装、缓存结构、事件匹配还是运行时日志

本 skill 的目标不是修业务逻辑，而是先判断 **问题在哪一层**。

---

## 一、先分清四层，不要混

### 1. skill 层

skill 只是说明书，负责：

- 什么时候用
- 怎么用
- 应该遵守什么规则

skill 不等于：

- 已经有真实工具
- 已经接入运行时
- 已经能自动触发

### 2. plugin / app / MCP 层

这一层才负责：

- 真正的可执行能力
- 工具发现
- 协议接入
- UI / 浏览器 / 桌面 / MCP server / app 能力

### 3. 安装 / 加载层

这一层负责：

- Codex 是否把本地插件当成“已安装插件”
- 目录结构是否满足加载器要求
- 配置是否启用
- 当前进程是否已经重新扫描

### 4. 触发层

这一层负责：

- hook 是否命中正确事件
- matcher 是否命中真实工具类型
- 输出是否真的写入日志或回显

**先判断是哪一层出问题，再动手。**

---

## 二、固定排查顺序

必须按下面顺序查，不要跳步。

### 第一步：确认是不是只有 skill，没有真实工具

先问自己：

- 当前只是有 `SKILL.md`，还是已经有真实 plugin / app / MCP / tool？
- 当前会话里的技能能不能只解释流程，不能真正执行？

如果只是有 skill，没有底层能力，就不要继续查 hook。

### 第二步：确认插件是否真的被启用

检查：

- `%USERPROFILE%\.codex\config.toml`
- 对应插件是否有：
  - `[plugins."name@marketplace"]`
  - `enabled = true`

如果没启用，先修配置。

### 第三步：确认插件是否真的“已安装”

不要把“文件存在”当成“已安装”。

重点查：

- `%USERPROFILE%\.codex\logs_2.sqlite`

关键错误：

- `plugin is not installed`
- `missing or invalid plugin.json`

如果日志有这类错误，说明问题还在安装 / 加载层。

### 第四步：确认缓存目录结构是否符合运行时预期

本地 marketplace 插件不要只看源目录，要看运行时缓存目录。

重点查：

- `%USERPROFILE%\.codex\plugins\cache`

如果官方缓存插件存在版本层或哈希层，就不要自己随便拍平目录。

优先对比：

- 官方缓存插件的目录层级
- 你自己的本地插件目录层级

如果结构不一致，先修结构，再谈重启。

### 第五步：重启后重新看日志，不要只凭感觉

重启后不要直接说“应该好了”，先查：

- 最新启动后的日志
- 同一时间窗口里有没有新的加载错误

如果旧错误消失，说明加载层可能已经过了。

### 第六步：再验证 hook 是否真的触发

只有加载层过了，才去做触发验证。

这一步要注意：

- hook 事件是否真实存在
- matcher 是否匹配你实际用的工具
- 不要用错误的工具类型做触发测试

例如：

- `Write / Edit / MultiEdit` 和 `shell_command` 不是同一类工具
- 一个 hook 对编辑工具有效，不代表对 shell 写文件也有效

---

## 三、固定判断标准

### 说明层问题

表现：

- 只有 skill
- 没有真实可执行能力

结论：

- 不是 hook 问题
- 不是重启问题
- 是能力根本没接进来

### 安装层问题

表现：

- 日志提示 `plugin is not installed`
- 或 `missing or invalid plugin.json`

结论：

- 文件存在但未被 Codex 识别为已安装插件
- 先查目录结构、缓存路径、安装产物

### 加载层问题

表现：

- 配置已启用
- 插件文件看起来正确
- 但新进程日志里仍有加载错误

结论：

- 还没达到运行时要求
- 不要继续做触发测试

### 触发层问题

表现：

- 加载错误消失
- 但 hook 没输出

结论：

- 优先查事件类型
- 优先查 matcher
- 优先查测试动作是否真的命中预期工具链

---

## 四、这类问题的固定经验

以后遇到类似问题，默认先套用下面这些经验：

### 1. skill 不等于工具

`SKILL.md` 只能说明“应该怎么用”，不能证明“已经能执行”。

### 2. 插件文件存在不等于已安装

Codex 可能还要求：

- 正确缓存路径
- 正确层级结构
- 安装状态
- 启用配置

### 3. 重启不是万能解

只有在：

- 配置正确
- 目录结构正确
- 加载器能识别插件

的前提下，重启才有意义。

### 4. 不要用错工具链做触发测试

hook 是否触发，和你实际用的是：

- 编辑工具
- shell 命令
- app 工具
- MCP 工具

直接相关。

### 5. 以日志为准，不以感觉为准

能证明“已加载”的证据优先级高于：

- 我觉得应该好了
- 我已经重启了
- 文件都在

---

## 五、建议的最小验证动作

每次排障都固定做这三件事：

1. 查最新日志里是否还有插件加载错误
2. 确认当前结构是否和官方缓存插件结构一致
3. 用正确类型的真实动作做一次最小触发验证

如果第 1 步没过，就不要做第 3 步。

---

## 六、禁止事项

排这类问题时，不要做下面这些事：

- 不要把 skill 文本当成工具接入完成
- 不要只靠重启反复试
- 不要在加载层没过时不停做触发测试
- 不要因为有一个源目录就假设运行时缓存也正确
- 不要在没有日志证据时宣称“已经生效”

---

## 七、最终目标

使用本 skill 时，最终必须给出明确结论：

- 现在卡在哪一层
- 下一步该查什么
- 哪些事情已经确认不是问题

避免再次出现：

- 问题还在安装层，却一直怀疑 hook 逻辑
- 只是 skill 有了，却误以为工具已经可执行
- 明明是目录结构错误，却反复要求重启
