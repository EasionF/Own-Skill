# 工程级编码设计规范

将用户关于功能、系统、工具、AI 项目或工程平台的需求，转化为完整、生产级、可执行、可验证、可维护、可演进的工程设计，为后续编码实现提供依据。

## 默认原则

- 默认完整设计，按工程标准展开。
- 设计先行，再进入编码执行。
- 默认产出一套主设计，不默认多方案发散。
- 不默认 MVP、demo、玩具级实现。
- 不只追求简单，而是追求工程正确性、完整性、可运行性、可维护性和真实交付。
- 主动补齐真实工程系统需要考虑的维度。
- 只把真正影响架构、成本、风险、数据模型、权限边界或长期维护的问题留给用户确认。
- AI 项目不是例外，只是在模型行为、工具、memory、评测、安全和漂移控制上有额外检查项。

只有在用户明确要求 MVP、原型、快速试验、简单实现、先跑起来时，才降低设计深度。

## 工程系统观

设计对象不是单个代码片段，而是工程系统。设计时必须考虑：

- 目标
- 边界
- 状态
- 数据
- 接口
- 工具
- 依赖
- 反馈
- 权限
- 约束
- 质量属性
- 演进机制

## 设计流程

1. 识别工程对象：判断用户要做的是功能、系统、模块、工具、Agent、RAG、MCP、数据管道、自动化工作流还是工程平台。
2. 建立系统上下文：明确它运行在哪里、服务谁、依赖谁、被谁调用、输出什么、失败影响什么。
3. 形成主设计：默认给出一套完整主设计。
4. 补齐工程维度：覆盖数据、接口、状态、异常、安全、性能、观测、测试、部署、迁移、验收。
5. 标出关键待确认点：只列真正影响方向、成本或风险的问题。
6. 交付给执行规范：产出可拆任务、可验证、可编码的实施依据。

## 默认输出结构

按任务复杂度调整篇幅，但默认覆盖以下部分：

1. 需求理解
2. 目标与非目标
3. 系统上下文
4. 关键约束
5. 总体架构
6. 模块与职责
7. 数据模型
8. 接口契约
9. 核心流程
10. 状态与生命周期
11. 错误处理与恢复
12. 权限与安全
13. 性能与扩展性
14. 可观测性
15. 测试与评测策略
16. 部署与配置
17. 迁移与兼容
18. 风险与开放问题
19. 实施阶段
20. 验收标准
21. 关键设计决策记录

## Reference 使用

按需读取 reference，不要一次性加载所有文件。

- 理论底座和成熟工程实践：读取 `references/engineering-principles.md`。
- 通用工程设计：读取 `references/design-checklist.md`。
- 后端服务/API/平台服务：额外读取 `references/backend-service-checklist.md`。
- 前端应用/交互工具：额外读取 `references/frontend-app-checklist.md`。
- CLI/SDK/插件/本地工具：额外读取 `references/tooling-checklist.md`。
- 数据管道/批处理/同步任务：额外读取 `references/data-pipeline-checklist.md`。
- AI/Agent/RAG/MCP 项目：额外读取 `references/ai-systems-checklist.md`。
- 需要交给编码执行 skill 落地：读取 `references/implementation-handoff.md`。
- 存在关键架构、接口、数据、安全、依赖或长期维护决策：读取 `references/decision-record.md`。

默认完整设计，但不要机械填表。以下情况可以压缩：

- 用户明确要求 MVP、demo、原型、快速试验。
- 单文件、低风险、边界清晰的小改动。
- 已有设计文档已经充分。
- 用户明确要求直接进入执行。

即便压缩，也必须保留：

- 目标
- 边界
- 主设计
- 验收标准
