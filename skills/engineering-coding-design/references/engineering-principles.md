# 理论底座与成熟工程实践

## 1. 系统工程原则

核心思想：

- 总体设计先行。
- 目标、约束、资源、风险要统一考虑。
- 子系统分解必须服务整体目标。
- 子系统之间的接口、责任和反馈要协调。
- 局部最优不能破坏整体可运行性。

落到编码设计：

- 先定义系统目标、边界和非目标，再设计模块。
- 先定义模块职责和接口，再进入内部实现。
- 设计要覆盖上下游调用方、外部依赖、数据流和运维场景。
- 任何新增模块都要说明它如何进入现有系统，而不是只说明它自己如何工作。

## 2. 工程控制论原则

核心思想：

- 系统有输入、输出、状态、反馈和控制目标。
- 稳定系统必须能感知偏差并纠正。
- 扰动、误差、延迟和失败路径必须进入设计。

落到编码设计：

- 显式设计状态机和生命周期。
- 明确哪些反馈用于修正系统行为。
- 设计重试、幂等、补偿、回滚、降级和人工介入。
- 对 AI/Agent 系统，额外设计行为漂移、工具失败、上下文污染和不确定输出的控制路径。

## 3. 成熟工程实践抽象

- Google Engineering Practices：强调设计、代码评审、可维护性和小步可审查变更。
- AWS Well-Architected Framework：关注卓越运营、安全、可靠性、性能效率、成本优化和可持续性。
- Azure Well-Architected Framework：关注可靠性、安全、成本优化、卓越运营和性能效率。
- The Twelve-Factor App：强调配置、依赖、进程、日志、环境一致性和可部署性。
- Google SRE：强调可靠性、监控、错误预算、可运维性和故障恢复。
- OWASP ASVS：把安全要求转成可验证的工程控制项。
- OpenTelemetry：把 traces、metrics、logs 作为可观测性设计的基础信号。
- C4 model：用上下文、容器、组件、代码层次表达架构。
- arc42：用结构化方式记录架构目标、约束、构建块、运行时视图、部署、质量和风险。
- ADR：记录关键架构决策、背景、后果和取舍。
- OpenAPI：用机器可读契约描述 HTTP API。

## 4. 设计判断准则

遇到不确定项时按以下顺序判断：

1. 是否满足用户目标和真实交付场景。
2. 是否保持系统边界清晰。
3. 是否让数据、状态和接口可验证。
4. 是否能在失败时恢复、降级或被人工接管。
5. 是否具备安全、性能、可观测性和可维护性。
6. 是否能被拆成可执行阶段。
7. 是否能被测试、评测或验收标准证明。
