# 工程级编码执行规范

在既定设计或明确目标下，以边界清晰、最小必要改动、可验证步骤、尊重现有代码和完整交付闭环的方式完成编码实现。

## 默认原则

- 目标对齐：先确认当前要完成的目标、范围和验收标准。
- 尊重现有系统：先读代码、配置、测试和现有模式，再动手改。
- 边界清晰：只改实现目标必需的文件和逻辑。
- 最小必要改动：在保证工程质量的前提下避免无关膨胀。
- 小步闭环：复杂任务分阶段实施，每一步尽量可验证。
- 验证优先：完成后运行测试、构建、类型检查、lint 或最接近的验证命令。
- 失败迭代：验证失败时定位原因、修复、再验证。
- 用户改动保护：不覆盖、回滚或清理不是自己造成的改动。
- 可审计交付：说明改了什么、为什么改、如何验证、还有什么风险。
- 不越权：不做用户没要求的架构重写、依赖替换、产品扩展或破坏性操作。

- 发现设计不可落地时，反馈设计问题和阻塞点，不私自改变架构方向。

## 默认执行流程

1. 读取上下文：需求、设计、相关代码、配置、测试和失败日志。
2. 确认执行边界：明确改哪些、不改哪些、风险在哪。
3. 制定短计划：复杂任务输出简短计划；简单任务直接执行。
4. 实施改动：遵循现有风格和局部边界。
5. 补充验证：写或更新测试，或至少运行现有验证命令。
6. 处理失败：失败就定位和修复；不能修就明确阻塞原因。
7. 收尾清理：清掉自己引入的死代码、无用 import、临时文件。
8. 交付说明：简明说明改动、验证和残余风险。

## Reference 使用

按需读取 reference，不要一次性加载所有文件。

- 执行步骤检查：读取 `references/execution-checklist.md`。
- 改动边界和用户改动保护：读取 `references/code-change-boundaries.md`。
- 验证策略：读取 `references/verification-checklist.md`。
- 调试和失败迭代：读取 `references/debugging-loop.md`。
- 最终交付格式：读取 `references/delivery-report.md`。

简单任务可以压缩流程，但不能跳过：

- 读相关代码。
- 明确改动边界。
- 完成必要修改。
- 做可用验证。
- 说明结果。
