# Memory Preflight

当任务进入实质性工程实现前，先使用本 skill。

适用场景：

- 写代码
- 改代码
- 写脚本
- 改配置
- 做 plugin / MCP / hook / app 接入
- 做自动化工具
- 搭运行链
- 做测试链路
- 写 skill 并配合执行逻辑落地

本 skill 的目标是：

- 先重新读取持久化 memory
- 先确认本次任务应遵守的规则
- 先确认是否允许最小可行实现
- 再开始设计和执行

---

## 一、固定前置动作

开始任何代码相关任务前，先读取：

- the current machine's configured persistent memory source, if one exists

### Memory MCP 自动恢复规则

如果任务要求使用 Memory MCP 作为前置记忆层，而 `memory-v3` 工具返回 `fetch failed`，不能直接进入 degraded mode。必须先检查当前机器的本地持久化记忆或已知运行记录中是否存在 Memory 服务启动方式。

在本机已知恢复方式存在时，必须先执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File C:\workspace\projects\agent-memory-knowledge-platform\.local\start-memory-stack.ps1
```

随后验证：

```powershell
Test-NetConnection 127.0.0.1 -Port 3101
Test-NetConnection 127.0.0.1 -Port 15432
```

验证通过后重试 `memory_health`。只有在启动失败、端口验证失败，或用户明确要求不要启动本地服务时，才允许降级继续，并且最终汇报必须说明具体失败点。

不要假设当前上下文里的记忆已经足够新，尤其在以下情况必须重新读取：

- 当前线程已经很长
- 任务方向发生切换
- 从讨论进入实现
- 从文档进入代码
- 从普通问答进入插件 / 接入 / 自动化建设

---

## 二、先提取当前任务相关约束

读取 memory 后，不要全文复述，只提取与当前任务直接相关的约束。

至少检查：

1. 是否必须使用绝对路径
2. 是否要求先设计后执行
3. 是否要求中文可读注释/说明
4. 是否要求 UTF-8
5. 是否要求环境层约束而不是仓库层约束
6. 是否默认按产品级目标理解任务
7. 是否允许最小可行实现

---

## 三、最关键检查：是否允许 MVP

对所有代码相关任务，默认结论是：

- **不允许先做最小可行实现**

除非用户明确要求以下任意一种：

- 最小版本
- 原型
- 验证版
- smoke path
- 分阶段 MVP

如果用户没有明确要求这些，就按：

- 完整可用
- 工程级
- 可验证
- 非演示性质

来设计和实现。

不要因为任务复杂，就自己退回到“先做个最小版”。

---

## 四、设计前必须明确的内容

在真正开始写代码前，先在心里或对用户明确这四件事：

1. 目标是什么
2. 本次实现的完整交付边界是什么
3. 不做哪些东西
4. 怎么验证完成

如果这四件事不清楚，就不要直接进入实现。

---

## 五、推荐输出格式

在进入实质性编码前，优先用简短结构表达：

- 目标
- 路径选择
- 风险
- 验证方式

如果任务是代码接入类，还要额外明确：

- 本次是否允许 MVP：默认不允许
- 本次是完整接入、完整工具、还是仅做验证

---

## 六、失败模式

本 skill 主要防这几类错误：

- 明明是工程任务，却直接开写
- memory 已经有规则，但执行时没按规则做
- 用户没说要 MVP，却自己做成最小可行版
- 把接入层问题写成演示层脚本
- 把完整工具建设做成一次性桥接

---

## 七、最终原则

只要任务涉及代码，就先做 memory preflight。

顺序固定为：

1. 重新读取 memory
2. 提取相关约束
3. 明确本次不默认走 MVP
4. 先完成设计
5. 再开始实现
